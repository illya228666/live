# Runtime modules and one continuous life

`RuntimeSession` is the synchronous owner of one world and controller. Both Godot live training and `live` use it. It never resets at `EpisodeSteps`. Fixed simulation time and 64-bit age/training counters are independent of UI framerate. The original episodic `SimulationSession` remains a compatibility adapter for `train`, old numerical tests and v1 imports; new mechanics do not register there.

## Run and activate

In Godot, click **Пакеты…** to import a package folder, `module.json` or ZIP and
activate it in the current life. These inputs can also be dropped directly onto
the simulation window. Multiple selected files or a ZIP bundle activate together.
The manager lists active packages and displays complete import/activation errors.
Imports validate hashes before publishing immutable versions to the current
catalogue; simulation continues during file work. Close the manager and return
from frozen evaluation with **E** before importing. Startup configurations remain
unchanged. The existing command-line inbox workflow is also available:

```powershell
./tools/build.ps1
./tools/live.ps1                         # continuous headless learning; Ctrl+C stops
./tools/live.ps1 -Steps 3000 -Checkpoint artifacts/checkpoints/example
./tools/run-godot.ps1 -Train             # same executor, package-owned presentation
./tools/activate.ps1 -Package hunger@1.0.0,food@1.0.0
./tools/runtime-smoke.ps1                # real DLL/physics/presentation upgrades and unload verification in Godot
```

Default packages are generated by `tools/package.ps1` under `artifacts/packages/<id>/<version>/`. `configs/runtime.json` selects the startup set. Remove hunger/food from a *startup configuration* to exercise adding them later; active removal is deliberately unsupported. Configuration `settings` entries override a package's settings on first installation. An upgrade uses the new version's manifest settings; resubmitting the same active version preserves its effective settings.

The development packaging script rebuilds the shipped 1.0.0 packages. Do not run it over a package catalogue used by a running experiment. Published versions are immutable: build a new directory/version for an update. Policy exports archive their actual packages, so later rebuilding development packages does not change the saved teacher.

An activation request contains an id and exact `{ id, version }` references. The producer writes a temporary file then renames it to `<id>.ready.json`. Runtime polls at step boundaries; `.tmp` files are ignored. The result is written atomically to `<id>.result.json`. A request can install/upgrade multiple packages together. Missing files, checksums, dependencies, cycles, schemas, feature widths, capacities, actions or presentation preparation reject the entire candidate.

## Author a package

The optional [wild boar package](wildlife.md) is a complete example with a separate
behavior DLL, Godot presentation DLL and external PNG. Its dedicated build prepares
the package without activating it or changing the startup package set.

Reference **ArtificialLife.Core**, target net10.0, implement `IRuntimeModule` and publish a manifest:

```json
{
  "id": "example", "version": "1.0.0", "apiVersion": 1,
  "assembly": "Example.dll", "entryType": "Example.Module",
  "logicHash": "SHA256_OF_DLL",
  "logicFiles": {"Example.deps.json": "SHA256_OF_DEPS"},
  "dependencies": [], "provides": [], "requires": [],
  "schemas": {"example.component": 1}, "settings": {}
}
```

`Register(ModuleBuilder)` declares components, sensors, legal actions and their handlers, drive descriptors, physical systems and an optional motivation policy. Type keys are stable logical strings, never module-local enum ordinals. Providers normalize their numbers; the current controller accepts four features per token/action and 256 registered observation/action types. Registration is append-only and frozen after preparation. A changed meaning needs a new logical key. Width/capacity belong to the controller, not the world contract.

Component registrations declare a logical key/schema, an applicability predicate and an initializer. Initializers run for matching existing entities at installation and matching future entities after systems create them. The agent participates in the same mechanism. Explicit system `After` dependencies define deterministic order; missing references and cycles fail preparation. Capability requirements check that an integration exists; exact package dependencies additionally pin the implementation version. Communicate across modules using versioned keys/value data, not CLR types owned by another plugin.

Action filters can restrict candidates contributed by an existing module, while preserving at least one executable action. Movement exposes its existing speed through the `movement.control` component; a future module can modify that value without editing movement code. Component schemas and the module's `stateSchemaVersion` must be migrated explicitly. Registrations are frozen after preparation, so runtime callbacks cannot silently change the active provider set.

All persistent state lives in `RuntimeWorld`: entities have stable ids, components have versions, module state is keyed, and `world.Random(stream)` keeps its state in the world. Use `ComponentData.Write/Read` for primitives or primitive arrays and `JsonElement` for structured data. Private plugin objects, tensors, CLR types, event delegates, and untracked `Random` instances are not persistent state. Settings use the primitive `RuntimeSettings` reader; serializing/deserializing collectible plugin types through global reflection caches can prevent unloading.

`Migrate(candidate, previousManifest)` installs or upgrades state on a copy. Preserve existing entity ids/positions, age/time and unrelated values. Upgrade the versions and fields of components owned by your module explicitly. Activation calls no global reset and advances no simulation time. Modules may add data and entities during migration. Keep modules stateless apart from immutable settings/registrations: candidate preparation and future replacement must not depend on hidden mutable instance state. External side effects are outside the transaction.

Only one `IMotivationPolicy` is active. It receives copied drive values and named scalar signals and returns a finite learning signal. The shipped Homeostasis package implements the original weighted error/improvement formula. Physical effects, observable signals, diagnostic drives and motivation remain separate contracts. A replacement motivation package can retain the same package id and change its entry implementation.

## Learning across changes

A logic, sensor, action, schema, dependency or motivation change creates a new conditions revision. Presentation-only updates preserve it. Runtime validates the new initial observations and actions before committing, then reads fresh observations before the next decision. There is no fabricated transition, reward or terminal event for installation.

The existing DQN keeps online/target weights, Adam and training counters. Replay entries carry revisions. Only contiguous entries from the current revision are sampled; old records remain in the bounded ring until naturally overwritten. Learning waits for current-revision warm-up. Exploration is temporarily raised to at least 0.3 and returns to the age-based schedule over 10,000 steps, configurable through learning options.

Uniform sampling remains the default. `prioritizedReplayAlpha > 0` enables TD-error priorities and `prioritizedReplayBeta` importance correction; the controlled continual experiment uses these options. A revision change clears priority eligibility as well as ordinary sampling eligibility, so emphasis on rare prediction errors cannot reintroduce obsolete transitions.

When the vocabulary extends during training, the DQN initially masks the new observation types out of pooling, then introduces them linearly after current-revision warm-up (10,000 introduction steps by default). This keeps the pre-installation representation at activation without changing online/target weights, Adam or network dimensions. The inference mask is included in policy exports, so a frozen teacher reproduces the actual policy at export. This introduction strategy remains subject to the behavioral acceptance experiment.

`IAgentController` owns its algorithm and receives complete transitions. Its general contract does not require replay, fixed tensor dimensions, independent frames or DQN. Conditions-change notification must be synchronous and nonthrowing after validated capacity; no network reinitialization is allowed in that notification. An active logic error freezes advancement and reports the failure; an incomplete transition is never submitted to the controller. Recovery of arbitrary partially executed logic is not automatic.

`CreateInferenceController` supplies the separate evaluation branch. A future recurrent controller must fork its temporal state and RNG there; the UI never assumes that greedy inference can safely advance training memory. The current stateless DQN shares read-only parameters while training is suspended.

Policy export v2 contains immutable weight/manifest generations and an atomically replaced `current` pointer, architecture id/config, ordered registries, training count and archived packages/checksums. Loading checks architecture, registry identity and package logic. This is an inference/teacher export, not optimizer/replay/world persistence. Compatible v1 checkpoints still import. `live --trajectory PATH` emits revision schema records and copied transitions as JSONL; this is a foundation for later distillation, not a distillation implementation.

## Godot presentation packages

Optionally publish `presentationAssembly`, `presentationType`, `presentationHash`, `presentationFiles` hashes and `presentationOrder`. Reference **ArtificialLife.Godot.Contracts** and implement `IGodotPresentation`. The host shares Core, Godot.Contracts and GodotSharp identities while loading the implementation in a separate collectible context. Headless never loads that assembly.

`Prepare(context, initialFrame)` performs allocations off the live scene tree; `Update(frame)` and `Draw()` receive only immutable copied data. Run arbitrary Godot presentation code on the main thread. `context.Own(node)` scopes nodes; `context.OnDispose(action)` scopes resource/event cleanup. Load assets from the package's version-specific directory, never overwrite another version's resources. `Dispose` must release every subscription, task, node/resource and delegate that could retain plugin code. Preparation failure rejects activation. A later render failure disables that renderer and leaves physical advancement intact.

The main view owns the grid, trails, charts and generic diagnostics. Temperature, food and agent graphics live in presentation libraries. The runtime Godot smoke checks additions, physical updates, presentation-only revision behavior, continuous age/training, and collection of old simulation and presentation contexts.

## Research acceptance

`continual --config configs/continual.json` pretrains without hunger, hot-installs Hunger/Food, continues the same life, and compares adapted, frozen and random policies. Full training seeds are 42, 73, 101, 211, 509; evaluation seeds are fixed independently. `--pilot true` uses only training-derived evaluation seeds and one training run for tuning. Reports include pre-installation thermoregulation as well as both post-installation needs, counters and complete settings. Passing technical tests alone does not establish continual learning: the hunger and retention thresholds in the report must pass too.
