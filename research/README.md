# Локальная исследовательская кампания

Текущая проверенная база: [thermal-v2](../configs/research-baseline.json),
[результаты проверки](../docs/temperature-scenario-v2-report.md).
`-Action add` для pilot/full проверяет suitability review каждого активного
фактора; по умолчанию берёт базу/review из `research/baseline.json`.
Если фактор не требует адаптации, исследователь обязан исправить параметры
сценария, повторить пассивный/активный контроль и зарегистрировать новую версию.
Одного предупреждения в отчёте недостаточно.

Готовая пустая кампания: `research/campaigns/local`. Рабочая ветка этого этапа —
`codex/research-campaign-infrastructure`. Многочасовое исследование ещё не запущено.
Работать из корня репозитория в **PowerShell 7.2+** (`pwsh`), на этом компьютере
проверено 7.6.5. Вычисления полностью локальные; API key, отдельный AI daemon и
облачные workers не требуются.

## Быстрый запуск следующей сессии

Дать Codex запрос: «Продолжай кампанию local на N минут; восстанови контекст через
tools/research.ps1, затем следуй research/RESEARCHER.md. Выбери следующий вопрос
на основе накопленных данных. Бюджет вычислений — …». Codex читает память,
исследует источники, реализует варианты и принимает решения в активной сессии.

```powershell
./tools/research.ps1 -Action context -Campaign local
./tools/research.ps1 -Action session -Campaign local -Minutes 120
./tools/research.ps1 -Action hardware
```

Для отдельной новой кампании `-Action init -Campaign name` создаёт ветку
`codex/research-name`. Существующую ветку скрипт сам не переключает. Начальные
пользовательские изменения не сбрасываются. Перед началом проверить `git status`.

## Зарегистрировать гипотезу и запустить

1. Прочитать `BASELINE.md` и регламент `RESEARCHER.md`.
2. Скопировать `research/hypothesis-template.json`, заполнить гипотезу, механизм,
   опровержение и прочитанные источники. Исходная собственная идея может иметь
   пустой список sources. Имена направлений свободные.
3. Реализовать подход, выполнить подходящие тесты, собрать Release CLI и пакеты
   штатным workflow (`./tools/build.ps1 -Headless`). Новый пакет публиковать
   неизменяемой версией. Составить обычный experiment JSON, начиная с дешёвого pilot.
4. До оценки зарегистрировать study с конкретным правилом решения:

```powershell
./tools/research.ps1 -Action add -Campaign local -Id h01-pilot `
  -Hypothesis research/my-hypothesis.json -Config configs/my-pilot.json `
  -Stage pilot -Metrics temperature.mae,temperature.outside `
  -DecisionRule 'Заранее записанное правило продолжения/отказа, baselines и допустимые компромиссы'
./tools/research.ps1 -Action run -Campaign local -Minutes 10
```

`add` использует существующий `experiment-prepare`: проверяет конфигурацию,
архивирует реальные пакеты, сохраняет seed/бюджеты/протоколы. Исполняемый CLI с
зависимостями копируется один раз на каждую сборку в bundles; его хеши проверяются
перед запуском. Новые исходники не меняют уже зарегистрированные trials.
Если забыть пересобрать CLI/пакет, запустится именно предыдущая сохранённая сборка:
команда сборки перед регистрацией обязательна при изменении реализации.

Перед подготовкой также проверяется fingerprint физики/профиля оценки/горизонта
и SHA256 доказательства пригодности. `-ScenarioReview PATH` задаёт review другого
сценария; полный протокол и копия доказательств сохраняются вместе со study.
Смена мотивации, learner или training budget не требует переаудита неизменной среды.
Новый фактор или изменение среды/оценки требует новой проверки. `-Stage diagnostic`
позволяет исследовать и исправлять плохие условия; это не допуск к научному сравнению.

Стадия `full` предназначена для полноценных сравнений на нескольких training seed
и независимых от подбора evaluation seed; `diagnostic` — для разбора конкретного
эффекта/ошибки. Это роли экспериментов, а не ограничения выбора научного подхода.
Смена физики/критериев после просмотра оценки требует новой регистрации. Не
переписывать конфигурацию существующего study для улучшения результата.

После run сравнение создаётся автоматически штатным `compare`. Результат анализа
и следующий шаг записывает исследователь:

```powershell
./tools/research.ps1 -Action note -Campaign local -Id h01-pilot `
  -Text 'Что найдено, включая отрицательные результаты, неопределённость и решение' `
  -Next 'Конкретная следующая проверка или full study; почему она нужна'
./tools/research.ps1 -Action context -Campaign local
```

## Ресурсы и время

Машина: i7-12700KF (12 ядер / 20 потоков), 15.85 GiB RAM, RTX 4060 Ti.
Текущий DQN использует LibTorch CPU. GPU не включается автоматически; новый backend
должен отдельно выбирать, фиксировать и проверять свои зависимости/детерминизм.

В campaign.json редактируются: maxParallel, threadsPerWorker,
reserveFreeMemoryGiB, workerMemoryEstimateGiB, minFreeDiskGiB,
computeSliceMinutes, sessionMinutes и trialTimeoutMinutes.
Значения по умолчанию: до двух workers × один поток, 2 GiB оценки памяти на worker,
2 GiB свободного резерва, 10 GiB свободного диска, срез 10 минут и таймаут trial 120 минут.
Перед срезом параллелизм уменьшается по текущей свободной RAM и CPU с резервом
двух физических ядер. Для тяжёлой архитектуры повысить оценку RAM на worker.
Это admission estimate, не жёсткая OS-квота памяти; пиковое потребление зависит от метода.

```powershell
./tools/research.ps1 -Action run -Campaign local -Minutes 20 -Parallel 2 -Threads 1 -TrialTimeoutMinutes 60
```

Потоки передаются через AL_COMPUTE_THREADS/OMP_NUM_THREADS/MKL_NUM_THREADS и
DOTNET_PROCESSOR_COUNT; DQN учитывает AL_COMPUTE_THREADS. Новый контроллер должен
явно учитывать свой CPU/GPU budget. Потоки входят в идентичность исполнения;
их смена для уже исполнявшегося study требует нового study id.

Бюджет среза и дедлайн сессии запрещают новые trials после истечения времени.
Текущие trials завершаются, поэтому это **мягкая граница**. Таймаут отдельного trial
и force stop прерывают его процесс. Дедлайн Codex включает также чтение/рассуждение:
его соблюдает активный исследователь, скрипт ограничивает только вычисления.

## Остановить и продолжить

В другом терминале или через текущий Codex:

```powershell
./tools/research.ps1 -Action stop -Campaign local          # drain: закончить текущие trials
./tools/research.ps1 -Action stop -Campaign local -Force   # прервать текущие workers
./tools/research.ps1 -Action context -Campaign local
./tools/research.ps1 -Action session -Campaign local -Minutes 60  # новый явно выбранный бюджет
./tools/research.ps1 -Action run -Campaign local -Minutes 10 -Resume
```

Без `-Resume` запрос stop сохраняется. Ctrl+C самого runner сначала включает drain,
повторное Ctrl+C запрашивает force. При аварийном завершении координатора новый
runner ждёт блокировку оставшегося worker; force stop проверяет PID, время старта
и путь frozen executable перед остановкой оставшихся процессов. Готовые trials
пропускаются. Прерванный trial стартует с его seed заново; checkpoint не является
сохранением optimizer/replay/world посреди жизни. Исходные audit-файлы сохраняются;
новая попытка имеет отдельный каталог attempts. Журнал и CONTEXT восстанавливаются
по реальным файлам результатов, даже если запись «completed» не успела попасть в журнал.

После падения сессии открыть тот же чат Codex либо новый чат с репозиторием и дать
`research/campaigns/local/CONTEXT.md`. CLI-альтернатива — `codex resume`
([официальная документация OpenAI](https://learn.chatgpt.com/docs/cli/reference)).
Никакое расписание самостоятельного пробуждения не создаётся. Вычислительный
терминал может ещё работать после окончания ответа; это не означает, что Codex
продолжает научную работу после остановки сессии или исчерпания лимита.

## Хранение и резервная копия

- `research/campaigns/<id>`: компактная история для Git — гипотезы/регистрации,
  journal.jsonl, FINDINGS.md, CONTEXT.md, настройки и начальный профиль машины.
- `artifacts/research/<id>`: полные config/package snapshots, immutable bundles,
  suite/result/JSONL/checkpoints, сравнения, process.json и runtime limits.
- Ничего автоматически не удаляется. Осмысленные коммиты исходников и памяти
  делать на исследовательской ветке; не включать чужие изменения без проверки.

После остановки/завершения workers можно сделать полную копию на локальный диск:

```powershell
./tools/research.ps1 -Action backup -Campaign local -Destination 'D:\ResearchBackup\local-2026-10-24'
```

Назначение должно быть новым каталогом вне исходных каталогов кампании. Копия
содержит память, полные артефакты и SHA256 manifest. Скрипт отказывается копировать
работающих workers. Восстанавливать в исходные пути workspace (они записаны в
frozen config); перенос с изменением путей оформлять как новую регистрацию.
Физическая поломка единственного диска не покрывается хранением на этом же диске.

## Короткий сквозной тест

`./tools/research-smoke.ps1 -WorkerMemoryGiB 0.5` проверяет гипотезу воспроизводимости на четырёх коротких
trials: последовательный reference → stop → параллельное resume → compare →
запись анализа/следующего шага → новый процесс восстанавливает context.
Повторный запуск готовой кампании проверяет сохранность байтов и времени записи
готовых result.json. Оценка 0.5 GiB относится только к этому маленькому smoke с
replay 512 и маленькой сетью; настройки рабочей кампании local остаются 2 GiB.
Тест проверяет фактический admission двух workers. По умолчанию создаётся новый
study id с UTC-временем. Явное повторение уже проверенного id возвращает его старое
доказательство; не выдаёт старый последовательный запуск за новый параллельный.
